# Sim rules (normative)

This file is the single specification both sim cores implement (spec §6.4, point 4).
`public/js/sim/` and `src/Sim/` cite these rule ids in comments. A change here needs the
same change in both cores, regenerated golden vectors, and a `CORE_VERSION` bump.

Status: **M0 draft**. Rules marked *provisional* will change while Gloamhollow is ported.

## Numbers

- **R-INT-1** Every number in sim state is an integer in [−(2⁵³−1), 2⁵³−1]. No floats, ever.
- **R-INT-2** Every intermediate product stays inside that range too. Bound it in a comment next to any multiplication of two non-constant values.
- **R-INT-3** Division truncates toward zero (`intdiv` in PHP, `idiv` in JS). Division by zero is an error, not a value.
- **R-INT-4** `isqrt(n)` = ⌊√n⌋ exactly, for 0 ≤ n ≤ 2⁵³−1 (an approximate root, then integer correction).
- **R-INT-5** `fdiv(a, b)` = ⌊a / b⌋ (rounds toward −∞). Used for cell indices: cell = fdiv(mm, 2400).
- **R-UNIT-1** Positions are in millimetres; one cell = 2,400 mm. Cell (i, j) spans x ∈ [2400·i, 2400·i+2400), z likewise. i runs west→east, j runs north→south (Gloamhollow's grid).

## Angles and trig

- **R-TRIG-1** Angles are integers; 4,096 units per full turn. Yaw 0 faces north (−z), and yaw increases counter-clockwise seen from above (Gloamhollow's convention).
- **R-TRIG-2** `sin(a)` = `SINE[a mod 4096]`, scaled by 2¹⁴. The table is `public/js/sim/data/sine4096.bin` (4,096 × int16 LE). Both cores refuse to start unless its SHA-256 equals `SINE_SHA256`. `cos(a) = sin(a + 1024)`.
- **R-TRIG-3** The table was generated once by `bin/gen-sine-table.mjs` (round(sin(2πi/4096)·2¹⁴), exact at the quarter points). Regenerating it is a rules change.

## Randomness

- **R-RNG-1** xoshiro128** on four uint32 words, every operation masked to 32 bits.
- **R-RNG-2** Seeding from a uint32 seed s: z₀ = s; zᵢ₊₁ = zᵢ + 0x9E3779B9 (mod 2³²); wordᵢ = fmix32(zᵢ₊₁) (MurmurHash3 finaliser). An all-zero state becomes [1, 0, 0, 0].
- **R-RNG-3** `below(n)` for 1 ≤ n ≤ 65,536 = ⌊next() · n / 2³²⌋.
- **R-RNG-4** Draws happen in a fixed order per tick: player, then foes in entity order, then links by ascending id (spec §4.9.5). So far idle foes (R-FOE-6) and flitting foes (R-FOE-10) draw, within their own update.

## World (the static map)

The contract is `world = Sim.load(gdf)`, `state = Sim.init(world, seed, mode)`, `events = Sim.step(world, state, input)`, `hash = Sim.hash(state)` (decision #10). The world is immutable and is not hashed; the state names it.

- **R-GDF-0** `Sim.load` takes the GDF file's bytes, never a parsed object, so both cores read the same values. The bytes must be UTF-8 with no BOM, at most 262,144 bytes, nested at most 12 deep (spec §7.2), and every number must be a plain integer literal (`-?(0|[1-9][0-9]*)`, not `-0`; no `.`, `e`, `E`). Objects stay objects: an empty object or a key outside R-CANON-3 is rejected, and the top level must be an object. Integers outside R-INT-1 are rejected.
- **R-GDF-1** `grid.w`, `grid.h` are integers in [3, 64]. Cells are row-major: index = j·w + i.
- **R-GDF-2** `grid.cells` is strict standard base64 (RFC 4648 §4): length a multiple of 4, `=` only as final padding, padding bits zero. Anything else is rejected.
- **R-GDF-3** The decoded bytes are run-length pairs `[count, code]`: count in [1, 255], code in [0, 8] (spec §7.1 cell codes). The runs must cover exactly w·h cells (decision #11).
- **R-WORLD-1** Every border cell is wall (code 0), so the sim never reaches a position outside the grid.
- **R-WORLD-2** The player spawns at the centre of `start.cell`, which must be room (1) or corridor (2), facing yaw 0. In Gloamhollow that is the Vestibule checkpoint (34, 60); the sealed stair (34, 61) is wall (decision #12).
- **R-WORLD-3** World id = the first 16 bytes of SHA-256 over the canonical GDF (R-CANON-*), as 32 lower-case hex characters. `init` stores it as `state.world`; `step` refuses a state whose `world` differs, and one whose `core` isn't this core's `CORE_VERSION` (an older state has another shape).
- **R-WORLD-4** The world can't be changed after load (the JS core keeps the grid out of reach; `init` and `step` refuse anything `load` didn't build). Anything that changes during play (doors, sprung slabs) lives in state.

## Zones and checkpoints

- **R-ZONE-1** `zones` is optional; when present it is a list of at most 16 objects with keys `id` (as R-ENT-1, unique among zones), `name` (a string), `rects`, `ceil` and optionally `checkpoint`, `tint` and `walls`; nothing else. `tint` is `[r, g, b]`, three integers 0–255, and `walls` is `brick` or `shelves`; both are renderer only (R-DRESS-*). `rects` holds 1–8 rectangles `[x, y, w, h]` with w, h ≥ 1, inside the grid. No cell lies in two zones (spec §7.3). `ceil` is an integer in [3000, 6500] mm (spec §4.2). A cell's zone is the zone whose rect holds it, or none.
- **R-ZONE-2** `checkpoint` has keys `cell`, `yaw` (0–4095) and optionally `reach` (`"enter"`, the default, or `"effect"`). At most 12 zones have one. The cell lies in its own zone, is room or corridor, holds no door or slab, and no prop footprint covers it (R-PROP-2).
- **R-CP-1** `state.checkpoints` lists the checkpoints reached this run, `{ zone, x, z, yaw, life }`, in the order they were first reached; `state.cp` is the index of the current one. `init` puts in one entry: zone = the zone of `start.cell` (−1 if none), the start cell's centre, yaw 0, and the initial life (R-CP-3). `state.cp` = 0.
- **R-ZONE-3** After R-CP-2, if the player's cell is in a different zone from `state.zone` (−1 for none), the link events `leaveZone(old)` (if old ≥ 0) and then `enterZone(new)` (if new ≥ 0) happen, and `state.zone` = new. `init` sets `state.zone` to the start cell's zone.
- **R-CP-2** Each tick after the doors move (R-DOOR-3), if the player's cell is in zone Z, Z has a checkpoint with reach `enter`, and Z's index is greater than the current checkpoint's zone (Gloamhollow's forward-only `cpOrder`), the player reaches it: the entry for Z is replaced, or appended if there is none, with the checkpoint cell's centre, its yaw and the current life; `state.cp` points to it; the step emits `{ e: "checkpoint", zone: id }`. Reach `effect` checkpoints are reached only by a `setCheckpoint` effect (with links, decision #20).
- **R-CP-3** A *life* is what a death rolls back (Gloamhollow `G`): `{ hp, oil, hooded, hung, flasks, pebbles, doors, floor, taken, revealed, mirrors, chests, braziers, bellSets, links, groups, boss, loot, foes }`, with `doors` the list of each door's `open`, and copies of `state.floor`, `state.taken`, `state.revealed`, `state.mirrors`, `state.chests`, `state.braziers`, `state.bellSets`, `state.links`, `state.groups`, the boss's status (`asleep`, `awake` or `dead`), and `foes`: each foe's carried loot `[loot, lf, lp]` in entity order (decision #70). Lessons are what a death keeps (Gloamhollow `L`, spec §3): `state.sprung` (plates sprung during play), `state.pits` (hidden pits found), `state.marked` (plates found with the probe) and `state.bridge` (bridge cells found), cell indices in the order found, and `state.sealed` (R-DOOR-5).

## Traps and death

- **R-TRAP-1** After the checkpoint check, the trap test looks at the player's cell (i, j) = (fdiv(x, 2400), fdiv(z, 2400)) and the offsets lx = x − 2400·i, lz = z − 2400·j. Only the *inner* part of a cell is armed: 288 < lx < 2112 and 288 < lz < 2112 (Gloamhollow's 0.12–0.88 of the cell). In the inner part:
  - plate (3) with no slab (R-SLAB-1) and not in `state.sprung`: the cell is appended to `state.sprung` and the player dies of `slab`;
  - hidden pit (4): the cell is appended to `state.pits` unless already there, and the player dies of `pit`;
  - void (5): the player dies of `chasm`;
  - vent (7) whose vent is firing (R-VENT-2): the player dies of `vent`.
  - an alcove (8) with an armed alcove entity (R-ALCOVE-1): it springs with the player inside (R-ALCOVE-2) and the player dies of its kind, `drown` or `tip`.
  Room, corridor and bridge (6) cells are safe, and so is an alcove cell without an alcove entity.
- **R-TRAP-2** Cells in `state.sprung` are solid (R-MOVE-4), like slabs.
- **R-EYES-1** Eyes keys: `id`, `type`, `zone` (a zone id) and `wake` (18–1800 ticks; spec §4.4: at least 0.6 s). At most one eyes entity per zone. `state.eyes` holds one meter per eyes entity, in entity order, starting at 0.
- **R-EYES-2** After R-TRAP-1 (if the player is still alive), for each eyes entity in order: if the player's cell is in its zone and the lantern is lit (R-POW-1: oil > 0, not hooded, not hung, not doused), the meter rises by 5, and the step emits `{ e: "eyes", id }` if it was 0. Otherwise the meter falls by 7, down to 0. Once every meter is updated, if any has reached 5 · its wake, the player dies of `eyes` (Gloamhollow: wake 1.0 s, cooling 1.4 × as fast).
- **R-VENT-1** Vent keys: `id`, `type` (`vent`), `cells` (1–64 cells, each code 7), `period` (2–1800 ticks), `phase` (0 … period − 1), `warn` (≥ 0) and `fire` (≥ 1), with warn + fire ≤ period and 5·fire ≤ 3·period (fire at most 60 % of the period, spec §4.4). Every code-7 cell belongs to exactly one vent (decision #17).
- **R-VENT-2** On the step that starts at tick n (`state.tick` before it advances), u = (n + phase) mod period. The vent warns while u < warn and fires while warn ≤ u < warn + fire. Gloamhollow: period 108, warn 27, fire 33 (3.6 / 0.9 / 1.1 s), phases 0, 36, 72 (0 / 1.2 / 2.4 s). Vents keep their cycle while the player is dead.
- **R-DEATH-1** Dying sets `state.dead = { cause, at: n }` (n as in R-VENT-2), adds 1 to `state.deaths`, sets the velocity and the remainders to 0, and emits `{ e: "death", cause }`. The rest of that living step (eyes, pick-up, oil burn, cooldowns) is skipped; tool presses (R-TOOL-1) have already happened. Causes so far: `slab`, `pit`, `chasm`, `vent`, `eyes`, `damage`, `needles`, `drown`, `tip`, `beast` (a foe's blow), `eater` (the Candle-Eater).
- **R-DEATH-2** While dead, a step does only this: R-RISE-1, then the doors move (R-DOOR-3, which never stops), then pebbles land (R-PEB-3). No movement, tools (hood, probe, pebble, oil, interact), oil burn, checkpoints, traps, eyes, pick-ups or cooldowns. `state.prevButtons` still updates and `state.tick` still advances.
- **R-DEATH-3** Ironman: after a death the run is over. `step` refuses a state with `dead` set in mode `ironman` (decision #19).
- **R-RISE-1** Rise (button 7) on its rising edge, on a step whose n ≥ at + 51 (1.7 s, Gloamhollow's death card, decision #18): pick the checkpoint. In `practice`, a target N ≠ 0 picks the entry with zone N − 1; if there's none, nothing happens. Otherwise (delve, or target 0) it's `state.cp`. Then: `state.cp` = that entry; the life comes back (hooded, doors' `open`; each door's t = 693 if open, else 0); hp = 3000 (100 hp); oil = max(life.oil, 50 · 30000); hung, flasks, pebbles, `state.floor`, `state.taken`, `state.revealed`, `state.mirrors`, `state.chests`, `state.braziers`, `state.bellSets`, `state.links` and `state.groups` come back from the life; the foes are reset (R-FOE-8), and so is the boss (R-BOSS-6); `state.player.busy` = 0; `state.sealing` = [] and `state.blows` = []; sealed doors stay shut; `state.zone` becomes the zone of the rise point, with no zone events; `state.player.calm` = 151; pebbles in flight are dropped (`state.flying` = []); every eyes meter is 0; the player stands at the entry's x, z with its yaw, pitch 0, velocity and remainders 0; `state.dead` = null; the step emits `{ e: "rise", zone }` (the zone's id, or null for −1). Nothing else happens on that step besides R-DEATH-2's door movement. Lessons stay.

## Entities (the placed things)

- **R-ENT-1** `entities` is optional; when present it is a list of at most 400 objects. Each has `id` (a string matching `^[A-Za-z_][A-Za-z0-9_]{0,31}$`, unique in the file) and `type`. The core knows the types `door`, `slab`, `prop`, `vent`, `item`, `eyes`, `bell`, `bellSet`, `lampHook`, `mirror`, `crystal`, `chest`, `alcove`, `foe`, `brazier`, `boss`, and the dressing types `torch`, `inscription`, `marks` and `decor` (R-DRESS-*); any other type is rejected (types are added as the core learns them). Each type allows exactly the keys listed below: a missing key or any other key is rejected.
- **R-ENT-2** `cell` is `[i, j]`, two integers inside the grid. At most one door or slab per cell.
- **R-ENT-3** An entity's *number* is 1 + its index in `entities`. The input's `target` names an entity by number; 0 names none (decision #15).
- **R-DOOR-1** Door keys: `id`, `type`, `cell`, `style` (`stone`, `grate` or `mask`), `opens` (`interact`, `trigger` or `key`), only when `opens` is `key` a `key` (the id of a key item), and only when the style is `mask`, `face` (`weep`, `laugh`, `sleep` or `blank`). The cell must be room or corridor and must not be `start.cell`.
- **R-DOOR-2** `state.doors` holds one `{ open, t }` per door, in entity order; `init` sets `open: false, t: 0`. `t` ∈ [0, 693] is how far the door has moved (693 = 33 · 21).
- **R-DOOR-3** Each tick, after the movement (or, while dead, after R-RISE-1), every door with `open` and t < 693 moves on: t = min(693, t + 21); every door without `open` and t > 0 moves back: t = max(0, t − 33). Opening takes 33 ticks (Gloamhollow 1.1 s), closing 21 (0.7 s).
- **R-DOOR-5** `state.sealed` (a lesson, R-CP-3) lists sealed doors by door index, in the order sealed. A sealed door never opens: R-ACT-1 and `openDoor` leave it shut, and a rise restores it shut.
- **R-DOOR-4** A door's cell is solid while 20·t < 17·693 (Gloamhollow: solid while `anim` < 0.85). A door opened on tick n stops blocking on tick n + 29.
- **R-ACT-1** Interact (button 5) on its rising edge, before movement, with `target` = N ≠ 0: if N = 1000 + k, the dropped loot `state.loot[k]` is picked up (R-THIEF-4); if entity N is a foe, the player reaches for a mimic (R-MIMIC-1; a foe that isn't disguised does nothing); if entity N is an item, R-ITEM-2 applies; if it is a bell, R-BELL-3; if it is a door that isn't open and (x − cx)² + (z − cz)² ≤ 2600² for the door cell's centre (cx, cz) and the player's position before this tick's move, the press *reaches* it: the link event `interact(N)` happens (R-LINK-5), and if the door isn't sealed and has `opens: "interact"`, or `opens: "key"` with its key in `state.taken` (decision #36; the key isn't used up), its `open` becomes true and the step emits `{ e: "door", id, open: true }`. Anything else does nothing: no error, no event. Facing isn't checked; choosing what to highlight is the client's job (Gloamhollow `nearestInteract`: reach 2.6 m, no line of sight).
- **R-SLAB-1** Slab keys: `id`, `type`, `cell`. A slab lies on a plate cell (code 3) that was sprung before the run began (Gloamhollow `PRE_SLABS`). Its cell is solid. Plates sprung during play are lessons in `state.sprung` (R-TRAP-1).
- **R-PROP-1** Prop keys: `id`, `type`, `kind`, `pos` (`[x, z]` in mm, integers with 0 ≤ x ≤ 2400·w and 0 ≤ z ≤ 2400·h) and `yaw` (0–4095). A prop is decor that blocks walking. Its footprint is fixed by its kind (Gloamhollow `addCircle` / `addBox`):

  | kind | footprint |
  |---|---|
  | `statue` | circle r 500 |
  | `stele` | circle r 550 |
  | `tree` | circle r 450 |
  | `post` | circle r 160 |
  | `plinth` | circle r 500 |
  | `lectern` | circle r 500 |
  | `sarcophagus` | box, half-extents 750 (x) × 1150 (z); at yaw 1024 or 3072 the half-extents swap |

  A box prop's yaw must be a multiple of 1024. A circle's yaw is only for the renderer.
- **R-PROP-2** The footprint's bounding square or box [x0, x1] × [z0, z1] (x0 = x − r, x1 = x + r, or x ∓ the half-extent) covers the cells fdiv(x0, 2400) … fdiv(x1 − 1, 2400), and the same for z. Every one of those cells must be inside the grid, must not be wall, a door cell, a slab cell, `start.cell` or a checkpoint cell.

## Dressing (renderer only)

Dressing is validated on load, counts as an entity (R-ENT-3) and is part of the world id, but no rule reads it: it never blocks, never takes a target (R-ACT-1 does nothing) and can't be named by a link (decision #56). *Text* below means a string of Unicode code points (counted as code points) with no character in U+0000–U+001F or U+007F–U+009F; *page text* also allows U+000A (a line break).

- **R-DRESS-1** Torch keys: `id`, `type` (`torch`), `cell` (room or corridor) and `wall` (`n`, `e`, `s` or `w`); the neighbouring cell on that side is wall. A captive flame on that wall.
- **R-DRESS-2** Inscription keys: `id`, `type` (`inscription`), `style` (`plaque`, `carving`, `scrawl`, `stele`, `book` or `look`), `title` (text, 1–80), `pages` (1–8 page texts, each at least 1 long, at most 1,500 together; spec §7.2), exactly one placement and optionally `caption` (text, 1–80: the line above the title) and `sig` (text, 1–80). Placements: `wall` = `[[i, j], side]` (cell room or corridor, the neighbour on `side` wall), `pos` = `[x, z]` (mm, 0 ≤ x ≤ 2400·w, 0 ≤ z ≤ 2400·h) or `on` = the id of a chest (shown when that chest is looked at, R-CHEST-*). At most 24 inscriptions.
- **R-DRESS-3** Marks keys: `id`, `type` (`marks`) and `cells` (1–256 cells, none wall, none twice in one entity): masons' marks, seen only with the lantern hooded (spec §4.2).
- **R-DRESS-4** Decor keys: `id`, `type` (`decor`), `kind` (`bones`, `burnt`, `scorch`, `candles` or `stair`), `pos` (as R-DRESS-2) and `yaw` (0–4095). Decor has no footprint.

## State, hash, input

- **R-CANON-1** Canonical form: JSON with keys sorted by byte order, no whitespace, integers in plain decimal (−0 → 0), `true`/`false`/`null`.
- **R-CANON-2** Strings: `"` → `\"`, `\` → `\\`, U+0000–U+001F → `\u00xx` (lower-case hex); everything else is raw UTF-8. Invalid UTF-8 or lone surrogates are errors.
- **R-CANON-3** Object keys match `^[A-Za-z_][A-Za-z0-9_]*$` (so PHP never turns a key into an int).
- **R-CANON-4** No empty objects in sim state (PHP can't tell `{}` from `[]`). Use a list or leave the key out.
- **R-HASH-1** `hash(state)` = the first 16 bytes of SHA-256(canonical(state)), as 32 lower-case hex characters.
- **R-INPUT-1** Input per tick: `move` [fw, strafe] ∈ [−127, 127]², `yaw` ∈ [0, 4095], `pitch` ∈ [−127, 127], `buttons` uint16, `target` uint16. Anything else is rejected **before** state changes.
- **R-INPUT-2** Buttons are levels. An action fires on its rising edge (pressed now, not on the previous tick), except strike, which repeats while held (R-STRIKE-1), and run (R-MOVE-1). Bits: 0 strike, 1 hood, 2 probe, 3 pebble, 4 oil, 5 interact, 6 run, 7 rise.

## Movement *(provisional)*

- **R-MOVE-1** Walk 3,200 mm/s, run 5,400 mm/s (Gloamhollow).
- **R-MOVE-2** If fw² + strafe² > 127², scale both by 127/isqrt(fw² + strafe²) (truncating).
- **R-MOVE-3** Target velocity: tx = speed·(−sin·fw + cos·strafe) / (127·2¹⁴), tz = speed·(−cos·fw − sin·strafe) / (127·2¹⁴). Velocity eases by `v += (t − v)·2/5` per tick (Gloamhollow's `min(1, dt·12)` at 30 Hz). Position moves by `(v + r) / 30` and keeps the exact remainder r, so no distance is lost.
- **R-MOVE-4** Collision (Gloamhollow `pushCircle`). The player is a circle of radius r = 360 mm. After the move of R-MOVE-3, run 3 passes. Each pass computes (ci, cj) = (fdiv(x, 2400), fdiv(z, 2400)) once, then visits dj = −1, 0, 1 and, inside that, di = −1, 0, 1. For each solid cell (gi, gj) = (ci+di, cj+dj): qx = clamp(x, 2400·gi, 2400·gi+2400), qz = clamp(z, 2400·gj, 2400·gj+2400), dx = x − qx, dz = z − qz, d2 = dx² + dz².
  If d2 = 0 (the centre is in or on the cell), x, z go back to the position before this tick's move. Else if d2 < r²: d = isqrt(d2), x = qx + idiv(dx·r, d), z = qz + idiv(dz·r, d). Later cells in the same pass see the updated x, z. Velocity and remainders are not changed. Bounds: |dx|, |dz| ≤ 2,760, so every product stays below 2²³.
  Solid cells: outside the grid, wall cells, door cells while R-DOOR-4 holds, slab cells and cells in `state.sprung` (R-TRAP-2).
  After the nine cells, the same pass visits every prop, bell and mirror in entity order (Gloamhollow's `obstacles`):
  - Circle of radius ρ at (px, pz): dx = x − px, dz = z − pz, d2 = dx² + dz², R = r + ρ. If 0 < d2 < R²: d = isqrt(d2), x = px + idiv(dx·R, d), z = pz + idiv(dz·R, d).
  - Box [x0, x1] × [z0, z1]: qx = clamp(x, x0, x1), qz = clamp(z, z0, z1), dx = x − qx, dz = z − qz, d2 = dx² + dz². If 0 < d2 < r²: d = isqrt(d2), x = qx + idiv(dx·r, d), z = qz + idiv(dz·r, d).
  - d2 = 0 does nothing for props (Gloamhollow only resets for cells).
  Bounds: |dx|, |dz| ≤ 64 · 2400, so d2 < 2³⁶; a push needs d2 < R² ≤ 910², so dx·R < 2²⁰.
  Then, for the player only, every foe that is asleep, idle or hunting (not dormant, rising, dead, gone or disguised): a circle of radius R = r + idiv(85·ρ, 100) for the foe's radius ρ (Gloamhollow `m.r * 0.85`), pushed as for circle props.
- **R-MOVE-5** The sim has no touch-stick speed. The client maps a touch stick onto `move` with run held: move = deflection · 127 · 8/9 (5.4 m/s · 8/9 = Gloamhollow's 4.8 m/s), after a 12 % dead zone (decision #16).

## Touch powers (spec §4.9.3, step 7b)

A power acts when its foe's blow lands (R-FOE-6), after the damage. A chance is `below(100) < p` (R-RNG-3), drawn right there, in the foe's own update (R-RNG-4). The step emits `{ e: "power", k, id }` (k the power, id the foe's) when a power takes hold. `init` and every rise (R-RISE-1) set the player's `doused` = false, `frozen` = `freezeImm` = `heldT` = `holdImm` = `confused` = `poison` = 0, `held` = −1 and `maxHp` = 3000. Living ticks count `frozen`, `freezeImm`, `heldT`, `holdImm`, `confused` and `poison` down by 1 (not below 0) with the cooldowns (R-TOOL-2).

- **R-POW-1** *Lit.* The lantern is lit when oil > 0 and it is not hooded, not hung and not doused (R-EYES-2, R-FOE-7 and the rest use this).
- **R-POW-2** Douse (aquator): if the lantern isn't hung, `doused` = true and `hooded` = false. A doused lantern burns no oil (R-OIL-1), can't light a brazier (R-BRAZIER-2: `needLight`) and can't be hung (R-HOOK-2: `lanternOut`). Hood (R-TOOL-1) on a doused lantern that isn't hung, with oil > 0, relights it: busy = 30, busyOn = −2 (R-BRAZIER-2's busy: no movement, no tools), `{ e: "busy", id: null }`; when busy ends, `doused` = false and `{ e: "relit" }`. With oil 0 it says `lanternOut`. Pouring oil (R-OIL-3) doesn't clear `doused`. A douse while a brazier is being lit (busyOn ≥ 0) stops it (busy = 0, busyOn = −1); a douse while relighting doesn't, and the relight still clears `doused` when it ends.

- **R-FOE-9** The step emits `{ e: "foe", id, st }` whenever a foe wakes (to rising or hunting), finishes rising, or turns hunting from idle; `{ e: "hit", id, hp }` and `{ e: "foeDead", id }` for blows; `{ e: "swing" }` for a swing.
- **R-FOE-10** Flitting (Lantern Delve's `flit`, kinds with `flit` = 1). In the step R-FOE-6 names: if ft > 0, ft − 1; at ft = 0, ft = 8 + below(9) and fa = below(4096) (two draws, R-RNG-4). The foe's move this tick, if it has one, and otherwise a move of its own (but none on the tick it starts winding up), uses the vector v = u + (idiv(9·cos fa, 10), idiv(9·sin fa, 10)), where u is the unit direction to its goal scaled by 2¹⁴ (idiv(ex·2¹⁴, e), likewise z; (0, 0) when it has no move this tick) and cos, sin are R-TRIG-2's; it moves by (idiv(vx·speed, 30·2¹⁴), idiv(vz·speed, 30·2¹⁴)) (|vx·speed| < 2¹⁵·4500 < 2²⁸). Lantern Delve's sideways wobble of the other fliers is not kept.
- **R-FOE-11** Regeneration (kinds with `regen` > 0): in each foe update, for each foe in entity order that is not dormant or dead: if hp < strikes, rg + 1, and at rg = regen, hp + 1 and rg = 0; at full strikes rg = 0. A rise resets rg with the rest of the foe (R-FOE-8).

## Braziers, the boss and the exit

- **R-BRAZIER-1** Brazier keys: `id`, `type` (`brazier`), `cell` (room or corridor, no door or slab) and `lit` (true or false: lit at the start). It blocks walking like a prop, a circle of radius 550 at its cell centre (in the push order), checked as in R-PROP-2. `state.braziers` holds each one's `lit`, in entity order.
- **R-BRAZIER-2** Interact with an unlit brazier while the boss (if any) isn't dead: reach 2300 from the cell centre, with line of sight; `interact(N)` happens. With oil > 0 and the lantern neither hung nor doused (R-POW-2), the player becomes busy: `state.player.busy` = 30, `busyOn` = the brazier's index (Gloamhollow 1.0 s), and the step emits `{ e: "busy", id }`; otherwise `{ e: "msg", k: "needLight" }`. While busy > 0 the player's move input counts as [0, 0] and the tool presses (R-TOOL-1, R-STRIKE-1) do nothing. At the end of each living tick that doesn't end in a death, after the cooldowns, busy − 1; at 0 the brazier lights (`{ e: "brazier", id, lit: true }`) (decision #49).
- **R-BOSS-1** The bestiary's `bosses` section holds `eater` (Ilvaris, the Candle-Eater, spec §4.9.3; Gloamhollow's numbers, seconds as ticks): strikes 6, damage 20, oilHit 8 points, radius 600, speeds 1750 / 2350 mm/s (phase 1 / 2), wakeAtk 45, wind 21, hitRange 2200, windRange 1700 (seeking: 1450), stop 1200, reel 9, tearWind 18 (the wind-up after being torn from a brazier, Gloamhollow 0.6 s), feed 69 / 51, feedReach 1300, feedCd 42, phase2Atk 27, phase2FeedCd 45, atk 48 / 36, solidRange 3600, drainRange 5500, drain 3000 / 4500 units per tick.
- **R-BOSS-2** Boss keys: `id`, `type` (`boss`), `kind` (a boss kind), `pos` ([x, z] mm inside its zone) and `zone` (a zone id). At most one boss. `state.boss` is null without one, else `{ st, x, z, hp, phase, t, atk, feedCd, target, feedHits }`, starting `asleep` at `pos` with hp = strikes, phase 1 and everything else 0 (target −1). Her box is the bounding box of her zone's rects, inset by 700 mm; she never leaves it.
- **R-BOSS-3** `wakeBoss` turns an asleep boss to `stalk` with atk = wakeAtk and emits `{ e: "boss", st: "stalk" }` (decision #48). Her status in the life is `asleep` (st asleep), `dead`, or `awake`.
- **R-BOSS-4** Boss update, on living ticks, right after the foes (R-FOE-6), unless she is asleep or dead. With d = max(1, isqrt(dx² + dz²)) to the player: she is *solid* while a lit brazier's centre lies within solidRange (squares, strictly). atk = max(0, atk − 1), feedCd = max(0, feedCd − 1). If d < drainRange, oil > 0 and the lantern isn't hung, oil −= idiv(drain·(5·drainRange − 3·d), 5·drainRange) (Gloamhollow 0.4 + 0.6·(1 − d/5.5)), down to 0, where the lantern goes out and un-hoods (`{ e: "msg", k: "lanternOut" }`). Then by state:
  - `stalk`: if feedCd = 0 and a brazier is lit, the nearest lit one (ties: entity order) becomes her target and she turns `seek`; else if d < windRange and atk = 0 she winds up (`wind`, t = wind); else if d > stop she moves towards the player at her phase's speed;
  - `seek`: if the target is out, `stalk`; else if d < seeking windRange and atk = 0, `wind`; else if her distance to the target's centre < feedReach, `feed` (t = feed for her phase, feedHits = 0, `{ e: "boss", st: "feed" }`); else she moves towards it at 11/10 of her speed;
  - `feed`: t − 1; at 0, or when the target goes out: a lit target goes out (`brazier` event); `stalk`, feedCd = feedCd;
  - `wind`: t − 1; at 0, if d < hitRange, oil −= oilHit (down to 0, where the lantern goes out and un-hoods as above) and the player is hurt for damage (cause `eater`); then `stalk`, atk = atk for her phase;
  - `reel`: t − 1; at 0, `stalk`.
  A move is (idiv(ex·speed, 30·e), idiv(ez·speed, 30·e)) as in R-FOE-6, then R-MOVE-4 against cells and props, then a clamp to her box.
- **R-BOSS-5** She is a strike target (R-STRIKE-1) unless asleep or dead, with radius 600 (a foe at the same distance wins); a blow on her (R-STRIKE-2, with no knock-back or stun) does nothing but `{ e: "boss", smoke: true }` unless she is solid (decided when the blow lands). A solid hit: hp − 1 (`{ e: "hit", id, hp }`). At 0 she is `dead`: every brazier lights, the link event `bossDefeated` happens, `{ e: "bossDead" }`. Otherwise, in phase 1 at hp ≤ 3: phase 2, `stalk`, atk = phase2Atk, feedCd = phase2FeedCd, and every brazier goes out (`{ e: "boss", phase: 2 }`). Otherwise, feeding: feedHits + 1, and at 2 she tears away (`wind`, t = tearWind); else, unless winding up, `reel` (t = reel). She pushes the player like a foe (R-MOVE-4, r + 0.85·600) unless dead.
- **R-BOSS-6** On a rise, a boss whose status in the life isn't `dead` starts again: asleep at `pos` with full strikes (decision #51); a dead one stays dead.
- **R-EXIT-1** `exit` (optional) has `cell` (room or corridor) and optionally `requires`: `bossDefeated`, or the id of a flask, treasure or key item (decision #50). On a living tick, after the pick-ups, if the requirement holds (the boss is dead / the item is in `state.taken`) and (x − cx)² + (z − cz)² < 1000² for the exit cell's centre, the run is won: `state.won` = n, `{ e: "won" }`, and `step` refuses the state afterwards.

## Links (spec §4.3)

- **R-LINK-1** `links` is optional; when present it is a list of at most 64 objects with keys `id` (an integer 1–65535, unique), `when`, `do` (1–16 effects) and optionally `undo` (1–16 effects; not allowed when `when` is event-valued, R-LINK-2), `repeat` (true or false, default false) and `delay` (0–600 ticks, default 0); nothing else.
- **R-LINK-2** A *term* is an object. A trigger term has exactly one key, the trigger, from this list:
  - events: `interact` (a door, item, bell, lamp hook, mirror, chest or brazier id), `itemTaken` (a flask, treasure or key id), `enterZone` and `leaveZone` (a zone id), `bellsWrong` (a bell set id), `linkFired` (another link's id);
  - events (cont.): `foesDefeated` (a group id), `bossDefeated` (true);
  - conditions: `foesAlive` (a group id: any of its foes awake or asleep), `bossAwake` (true: the boss is awake), `lightLit` (a brazier id), `doorOpen` (a door id), `inZone` (a zone id), `hasItem` (a flask, treasure or key id), `lanternHooded` and `lanternHung` (true or false), `bellsSolved` (a bell set id), `beamHits` (a crystal id), `linkActive` (another link's id).

  A gate term has exactly one of `all`, `any`, `atLeast`, `sequence` or `not`, plus its options. `all`, `any`, `atLeast`: a list of 2–8 terms; option `within` (1–1800, default 90); `atLeast` also needs `k` (1 … the number of terms). `sequence`: a list of 2–8 event triggers; options `within` (1–1800; without it there is no time limit, decision #27), `strict` (true or false, default false) and `onWrong` (1–16 effects, only with `strict: true`). `not`: one condition-valued term (a condition trigger, or an `all`, `any`, `atLeast` or `not` gate). Event triggers and `sequence` gates are *event-valued*; the rest are condition-valued. Gates nest at most 4 deep, and a link's `when` holds at most 16 triggers. Unknown keys, wrong id types and ids that don't exist are rejected. *(Cycles in the link graph are the publish validator's job, spec §7.3; the 8-pass limit bounds the sim either way.)*
- **R-LINK-3** Effects are objects with one key: `spawnFoes` (a group id), `wakeBoss` (the boss id), `lightOn`, `lightOff` (a brazier id), `setCheckpoint` (a zone id with a checkpoint), `openDoor`, `closeDoor`, `sealDoor` (a door id), `reveal`, `hide` (a hidden item's id), `damage` (1–1000) or `message` (a string of at most 1000 bytes of UTF-8).
- **R-LINK-4** `state.links` holds one entry per link in ascending id order: `{ val, active, spent, pend, m }`. `val` is the last value of `when` (false at first); `active` is true from the link's firing to its falling edge; `spent` is true once a link without `repeat` has fired; `pend` is the queue of delayed effect lists, `{ left, undo }` each, oldest first (decision #31); `m` is the memory of the `when` tree, one slot per event trigger inside it (its last tick, −1 for never) and three per `sequence` (progress, the tick of the last step, the tick it completed; 0, −1, −1 at first), in depth-first order.
- **R-LINK-5** Link events happen during a living tick, each as (kind, argument): entity number, zone index, bell set index, group index or link id. Those before link evaluation form batch 0, in the order they happened; the `linkFired` events of pass k form batch k. A batch is delivered once to every link, before the pass that follows it (batch 0 before pass 1). For each trigger term inside the `when` tree, in depth-first order:
  - an event trigger that isn't a step of a `sequence` records the tick if the batch holds its event;
  - a `sequence`: if progress > 0, it has a `within` and the tick − the last step's tick > within, progress = 0. Then, repeatedly, if an event of the batch not used yet equals step `progress`, it is used, progress + 1 and the last step's tick = this tick; when progress reaches the number of steps, the completion tick = this tick, progress = 0, and the batch is done for this sequence. If the batch is done without completing, and the sequence is strict, and an unused event of the batch equals any step, progress = 0 and its `onWrong` list is queued; the queued lists of one link apply, in tree order, once its whole `when` has been delivered, before the next link's delivery.
- **R-LINK-6** Values, on tick n. An event trigger is true if its last tick is n, or, inside an `all`, `any` or `atLeast` gate, if its last tick ≥ 0 and n − last < that gate's `within` (the innermost enclosing one). A `sequence` likewise, with its completion tick. Conditions read the state as it is: `doorOpen` the door's `open`; `inZone` the player's cell; `hasItem` `state.taken`; `lanternHooded` the hood; `lanternHung` whether the lantern hangs on a hook; `bellsSolved` the set; `beamHits` R-BEAM-2; `linkActive` the link's `active`. `all`: every term; `any`: one at least; `atLeast`: k at least; `not`: the term is false.
- **R-LINK-7** Link evaluation runs on living ticks only (decision #30), last in the step, after the pebbles land (R-PEB-3), and only if the player is alive. First, for every link in ascending id order, each entry of `pend` counts down: left − 1; the entries that reach 0 leave the queue and their `do` (or `undo`) lists apply, oldest first. Then up to 8 passes, each delivering the waiting batch (R-LINK-5) and visiting the links in ascending id order:
  - rising edge (`when` true, `val` false): if `pend` holds undo entries, they are dropped and the link is active again; otherwise, unless `spent`, the link fires: `active` = true, `spent` = true if it doesn't repeat, `linkFired(id)` joins the next batch, the step emits `{ e: "link", id }`, and `do` applies now (delay 0) or `{ left: delay, undo: false }` joins `pend`;
  - falling edge (`when` false, `val` true) of an active link: `active` = false. If `when` is event-valued, nothing else happens: its queued effects still land (decision #31). Otherwise, if `pend` holds do entries they are dropped (and no undo runs); else its `undo`, if any, applies now or `{ left: delay, undo: true }` joins `pend`;
  - `val` = the new value.

  Another pass follows if this pass applied an effect that changed the state or raised a `linkFired`, up to 8 passes in all. If an effect kills the player, evaluation stops there: during a pass, after that link's `val` is updated; during the countdown or an `onWrong`, before any `val` changes.
- **R-LINK-8** Effects, in list order: `openDoor` sets a door's `open` unless it is sealed or open (emits `door`); `closeDoor` clears it if set (emits `{ e: "door", id, open: false }`); `sealDoor` adds the door to `state.sealed` and clears `open` (emits `{ e: "door", id, open: false, sealed: true }` the first time); `spawnFoes` wakes the group's dormant foes (R-FOE-4); `wakeBoss` wakes an asleep boss (R-BOSS-3); `lightOn` / `lightOff` light or put out a brazier (emitting `{ e: "brazier", id, lit }`); `setCheckpoint` reaches that zone's checkpoint as in R-CP-2, whatever its reach and order (decision #20), saving the life as it is at that point in the list, so later effects of the same list aren't in it; `reveal` appends the item's entity number to `state.revealed` unless there, `hide` removes it; `damage` hurts (R-HP-2); `message` emits `{ e: "message", text }` and changes nothing. Applying a door, `reveal` or `hide` effect twice changes nothing more; `damage` hurts each time.

## Tools and items

- **R-TOOL-1** Tool presses are handled on their rising edge at the start of a living tick, before movement, in button order: hood (1), probe (2), pebble (3), oil (4), interact (5). They see the player's position before this tick's move and the yaw of this tick's input. Forward is (fx, fz) = (−sin yaw, −cos yaw), each scaled by 2¹⁴; a point at distance d along it is (x + idiv(fx·d, 2¹⁴), z + idiv(fz·d, 2¹⁴)). Bounds: |fx·d| ≤ 2¹⁴ · 8600 < 2²⁸.
- **R-TOOL-2** `probeCd` and `pebbleCd` (in `state.player`, and with them `strikeCd` and R-POW's timers) count down by 1 at the end of each living tick that doesn't end in a death, to 0. A probe needs probeCd = 0 and sets it to 21 (0.7 s); a throw needs pebbleCd = 0 and sets it to 15 (0.5 s). Death doesn't reset them.
- **R-PROBE-1** Reach r = 2050; if the point at r lies in the player's own cell, r = 2600. For s = 1 … 8, the point at idiv(r·s, 8): the first one in a solid cell (R-MOVE-4) that isn't a slab or sprung plate ends the probe with `{ e: "probe", k: "wall" }`. Otherwise the point at r names the probed cell (Gloamhollow `probeTarget`).
- **R-PROBE-2** By cell code: plate with a slab or sprung → `slab`; plate in `state.marked` → `plateKnown`; other plate → appended to `state.marked`, `plate`. Hidden pit in `state.pits` → `pitKnown`, else appended, `pit`. Void → `void`. Bridge → appended to `state.bridge` unless there, `bridge`. Vent → `vent`. Alcove: an armed `tip` alcove springs (R-ALCOVE-2) → `tip`; otherwise `alcove`. Anything else → `stone`. The step emits `{ e: "probe", k }`. Before any of this (and before the wall check), R-CHEST-3 may take the probe.
- **R-PEB-1** `state.player.pebbles` starts at 10, at most 12. A throw with none left emits `{ e: "msg", k: "pouchEmpty" }`. Otherwise pebbles − 1, pebbleCd = 15, and the range is want = clamp(6200 + idiv(6000·pitch, 127), 1600, 8500) mm: the int8 pitch maps linearly onto Gloamhollow's ±1.2 rad (decision #22).
- **R-PEB-2** The flight is marched from d = 400 in steps of 120 while d < want: at each point, a solid cell (R-MOVE-4) that isn't a slab or sprung plate stops the march; a slab or sprung plate becomes the landing point and stops it; any other cell becomes the landing point and d grows by 120. The landing point starts as the player's position. The pebble flies for T = idiv(21000 + 3·d + 1999, 2000) ticks (Gloamhollow 0.35 s + 0.05 s per metre, rounded up) and lands on the step at tick n + T − 1, n being the throw's step; `state.flying` gets `{ x, z, at }`. The step emits `{ e: "throw" }`.
- **R-PEB-3** At the end of every step, dead or alive, pebbles in `state.flying` whose `at` is this step's tick land, in list order, and leave the list. By the landing cell: slab or sprung plate → it rests; an alcove with an armed alcove entity whose door is open → it springs (R-ALCOVE-2), the pebble is gone, `alcove` (Gloamhollow `landPebble`); plate → appended to `state.sprung` (the slab falls, nobody dies), the pebble is gone; hidden pit → appended to `state.pits` unless there, gone; void → gone; bridge → appended to `state.bridge` unless there, rests; anything else → rests. Resting appends `{ x, z }` to `state.floor`. The step emits `{ e: "land", k }` with k = `slab`, `alcove`, `plate`, `pit`, `void`, `bridge` or `floor`.
- **R-PEB-4** After the eyes (R-EYES-2), a living player picks up pebbles: for each entry of `state.floor` from last to first, if pebbles < 12 and (x − px)² + (z − pz)² ≤ 750², it leaves the list and pebbles + 1 (Gloamhollow `pickPebbles`).
- **R-OIL-3** Oil (button 4): with no flasks → `{ e: "msg", k: "noFlasks" }`; with oil ≥ 96 points → `{ e: "msg", k: "lanternFull" }`; otherwise flasks − 1, oil = min(100, oil + 60) points, and `{ e: "oil", relit }` (relit: oil was 0). `state.player.flasks` starts at 1.
- **R-ITEM-1** Item keys: `id`, `type`, `kind` (`flask`, `rubble`, `treasure` or `key`), either `cell` or `in` (a chest id, decision #35; not for rubble), for treasure only `value` (1–100000), and optionally `hidden` (true; not for rubble or items in a chest). A hidden item can't be taken until it is revealed (R-LINK-8, decision #33). The cell is room, corridor or bridge and holds no door or slab (decision #23). An item in a chest is taken only by opening the chest (R-CHEST-2).
- **R-ITEM-2** Interact (R-ACT-1) with target = an item: the item's point is its cell centre, or for rubble the centre − (300, 300); its reach is 1700 (rubble 1600). It needs (x − ix)² + (z − iz)² ≤ reach² and line of sight (R-LOS-1) to the point. A flask, treasure or key lying in a cell, not in `state.taken`, and not hidden unless in `state.revealed`, is appended to it (by entity number); a flask adds 1 to flasks; the link events `interact(N)` and `itemTaken(N)` happen. Rubble with pebbles < 12 sets pebbles to 12 and stays; `interact(N)` happens. The step emits `{ e: "item", id, kind }`. Anything else does nothing.
- **R-LOS-1** Line of sight from the player (px, pz) to a point (ix, iz) (Gloamhollow `los`, aimed 300 mm short): ex = ix − px, ez = iz − pz, e = isqrt(ex² + ez²); the aim is (ix − idiv(ex·300, e), iz − idiv(ez·300, e)), or the point itself if e = 0. With v = aim − player, L = isqrt(vx² + vz²) and n = idiv(L + 599, 600), the points player + (idiv(vx·s, n), idiv(vz·s, n)) for s = 1 … n − 1 must not lie in a wall cell or a door cell while R-DOOR-4 holds.

## Lantern *(provisional)*

- **R-OIL-1** 1 oil point = 30,000 units (100 points = full). Burn per tick: 80 open, 25 hooded (0.08 / 0.025 points/s); none while doused (R-POW-2).
- **R-OIL-2** Hood toggles on the press (R-TOOL-1), only if oil > 0 and the lantern isn't hung or doused (a doused lantern relights instead, R-POW-2) (else `{ e: "msg", k: "lanternHung" }`). After the eyes and pickups, oil burns (R-OIL-1); at oil 0 the lantern goes out and un-hoods.
